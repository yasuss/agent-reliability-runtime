# 03 — Runtime Contracts

## 3.1 Run contract

A run has immutable identity and explicit status.

Required statuses:

`CREATED | RUNNING | WAITING_APPROVAL | COMPLETED | REJECTED | FAILED | BUDGET_EXCEEDED | CANCELLED`

Required fields include:

- `run_id`
- `workspace_id`
- `user_id`
- `request_text`
- `scenario_id` when launched from a fixture
- `provider_id`
- `model_id`
- `policy_version`
- `status`
- timestamps
- model/tool step counters
- terminal reason when non-complete

No success label may be inferred from a natural-language final answer.

## 3.2 Chat provider contract

Use one project-owned interface, conceptually:

```python
class ChatProvider(Protocol):
    async def complete(self, request: ChatRequest) -> ChatResult: ...
```

`ChatRequest` contains messages, JSON-schema-described tools, model settings and trace context. `ChatResult` contains text, structured tool calls, usage when available, finish reason, model/provider identity and raw-provider metadata only when explicitly safe to retain.

Mandatory implementations:

- `OpenAICompatibleChatProvider` — base URL + API key + model configuration. It must work with Ollama's OpenAI-compatible endpoint and be configurable for vLLM.
- No vendor-specific business logic may leak into the graph.

The acceptance path uses Ollama. vLLM is contract-tested; a live vLLM run is hardware-dependent.

## 3.3 Embedding provider contract

Separate embeddings from chat.

Mandatory local adapter: Ollama embedding API using `qwen3-embedding:0.6b`.

Optional adapter: generic OpenAI-compatible embeddings endpoint if implementation remains small. The RAG service consumes the interface, not Ollama directly.

## 3.4 Retrieval contract

Supported source formats in v1: UTF-8 `.md` and `.txt` files under the canonical knowledge directory.

Deterministic pipeline:

1. stable document ID from repository-relative path;
2. heading-aware deterministic chunking;
3. target chunk size approximately 1,200 characters with overlap capped at 150 characters when a section must be split;
4. embedding calculation;
5. PostgreSQL storage with `tsvector` and `vector` representation;
6. lexical top-20 + vector top-20 retrieval;
7. Reciprocal Rank Fusion with fixed `k=60`;
8. final top-6 evidence chunks;
9. every evidence item carries document ID, chunk ID, title and repository-relative source path.

The final answer may cite only evidence IDs that were actually retrieved in that run.

## 3.5 MCP tool contract

The OpsDesk MCP server exposes exactly these v1 tools:

1. `get_incident(incident_id)` — read-only.
2. `get_service_status(service_id)` — read-only.
3. `add_incident_note(incident_id, note, idempotency_key)` — side effect.
4. `restart_service(service_id, reason, idempotency_key)` — side effect.
5. `send_notification(channel, message, idempotency_key)` — side effect.

The server is deterministic and self-contained; it uses fictional state only.

MCP annotations may be exposed for interoperability but are **not trusted as the authorization oracle**. A project-owned trusted tool-policy registry is authoritative for risk classification.

## 3.6 Policy contract

Trusted policy classes:

- `READ_ONLY` — can execute without human approval after schema validation.
- `SIDE_EFFECT` — requires a valid approval bound to the exact action.

Policy input must include run identity, tool name, normalized arguments, trusted risk class and policy version. Model text, RAG documents, memories and MCP tool output cannot override the policy.

## 3.7 Approval contract

Approval object minimum fields:

- `approval_id`
- `run_id`
- `action_id`
- `tool_name`
- canonical normalized arguments
- `action_digest`
- `policy_version`
- `risk_class`
- `status = PENDING | APPROVED | REJECTED | EXPIRED | CONSUMED`
- created/decided timestamps
- optional expiry timestamp

`action_digest = SHA-256(canonical JSON of run_id + tool_name + normalized_args + policy_version)`.

Execution is allowed only if:

- approval status is `APPROVED`;
- run/tool/arguments/policy version reproduce the digest;
- approval is not expired;
- approval has not already been consumed for a different effect receipt.

Changing any material argument invalidates the approval. Approval is not a general permission grant.

## 3.8 Side-effect/idempotency contract

Every side-effecting tool call requires an `idempotency_key` generated by the trusted runtime before approval.

The MCP server must atomically persist an effect record with a uniqueness constraint over the logical effect identity. On a repeated call with the same key and identical digest, it returns the original effect receipt and does not apply the effect again. Same key + different action digest is an error.

A timeout or process crash after dispatch therefore cannot justify blind duplicate execution.

## 3.9 Memory contract

Thread/checkpoint state is not long-term memory.

Long-term memory fields include:

- memory ID
- workspace/user scope
- kind: `PREFERENCE | VERIFIED_FACT | OBSERVATION`
- provenance: `USER_EXPLICIT | TOOL_VERIFIED | MODEL_OBSERVATION`
- trust: `TRUSTED | UNTRUSTED`
- content
- created/updated timestamps
- optional source run/tool reference

Rules:

- Memory may influence context, personalization or retrieval hints.
- Memory must never grant tool authority, skip approval or alter trusted policy classification.
- `MODEL_OBSERVATION` is untrusted by default.
- User can list and delete memories through API/CLI.
- The poisoning test injects a memory instructing the agent to bypass approval; the runtime must still block side effects.

## 3.10 API contract

Mandatory local HTTP endpoints:

- `POST /api/v1/runs`
- `GET /api/v1/runs/{run_id}`
- `GET /api/v1/runs/{run_id}/events`
- `POST /api/v1/runs/{run_id}/approvals/{approval_id}`
- `GET /api/v1/memory`
- `DELETE /api/v1/memory/{memory_id}`
- `GET /healthz`
- `GET /readyz`

No streaming transport is required for v1. Polling is sufficient.

## 3.11 CLI contract

A standard-library `argparse` CLI is sufficient. Required commands:

- `ingest`
- `run --scenario <id>` or `run --task <text>`
- `eval`
- `export-replays`

The CLI is a developer/reproducibility surface, not a second product UI.
